# 🛠️ Development & Deployment Guide

This document maps out dependencies, systemic pre-requisites, configuration parameters, and execution vectors required to stand up, optimize, and maintain the **AI Code Scientist** environment.

---

## 📋 System Prerequisites & Environmental Baselines

Before executing deployment procedures, verify your target runtime environment complies with the following infrastructure definitions:

1. **Container Engine:** Podman Engine (`>= 4.4.0`) or Docker Engine (`>= 24.0.0`).
2. **Orchestration Utility:** `podman-compose` or `docker-compose` v2 interface.
3. **Hardware Acceleration Engine:** An active CUDA/NVIDIA container runtime setup on the host machine to anchor localized model parameters inside VRAM. The baseline models inside this stack are optimized to seamlessly fit inside an **NVIDIA RTX 5070 Ti (or equivalent >= 12GB VRAM allocation)**.
4. **Local LLM Server:** Ollama running natively on the host workstation/server, listening over the network interface (standard binding address: port `11434`).

---

## 📥 Host Model Provisioning (Ollama Setup)

Your local LLM engine must have the target model layers pre-cached before launching the agent runtime. Execute the following allocations on the host machine hosting your Ollama daemon:

```bash
# Pull the optimized context extraction and orchestration worker
ollama pull qwen3.5:9b

# Pull the dedicated software architecture generator
ollama pull qwen2.5-coder:14b

# Pull the heavy-reasoning validation model for code analysis
ollama pull deepseek-r1:14b
```

Verify your host local inventory matches standard outputs:
```bash
ollama ls
```

## ⚙️ Configuration Setup (`app.py` Optimization)

The agent suite is configured to handle resource distribution across your hardware dynamically. The global runtime mappings are exposed via the `MODEL_CONFIG` vector at the head of `app.py`:

```python
# Head configuration blocks inside app.py
MODEL_CONFIG = {
    "searcher": "qwen3.5:9b",          # Light, fast network query extraction
    "processor": "qwen3.5:9b",         # High token processing speed for raw content
    "expert": "qwen2.5-coder:14b",     # Specialized target generation logic
    "critic": "deepseek-r1:14b"        # Deep-chain logical safety validation
}
```

### Failsafe Boundary Constraints
To insulate computing hardware from running infinitely during recursive repair loops, the background orchestrator maintains an execution guardrail. 

Inside `app.py`, under `run_agent_pipeline_background()`, the loop exhaustion parameter dictates total permissible iterations:
```python
# Iterative repair threshold configuration
if approved or loop_count >= 10:
```
*Modify this value downward (e.g., `3`) for high-speed pipelines, or upward (`10`) for deep, continuous autonomous self-healing cycles.*

## 🚀 Deployment Instructions (Automated Up-time)

The ecosystem handles builds, configuration generation, cache resets, and volume linking via the custom `install.sh` utility script.

### 1. Provision Execution Permissions
```bash
chmod +x install.sh
```

### 2. Initialize Infrastructure Setup
Run the setup utility. The system will prompt you for your explicit host network IP address tracking your Ollama setup:

```bash
./install.sh
```

```text
===============================================
   Konfiguration av AI Code Scientist   
===============================================

Ange URL till din Ollama-instans [http://192.168.68.100:11434]: 
```
*Hit **Enter** to accept default network routings or explicitly assign targets.*

### What happens under the hood during this execution sequence?
1. Generates a safe local `.env` containing your target routing URLs.
2. Forcibly tears down older instances (`podman-compose down`) to free up active socket bindings.
3. Purges structural builder caching layers (`podman builder prune -f`) to ensure recent local code mutations inside `app.py` are explicitly packed into new images instead of pulling stale runtime layers.
4. Mounts the specified permanent data volumes to preserve application metrics across environment wipes.

## 📦 Volume Architecture & State Persistence

The system uses three strict persistent volume mappings declared across `docker-compose.yml` to guarantee zero-data-loss execution topologies:

```yaml
    volumes:
      - .:/app
      - sqlite_data:/app/db_data            # Retains relational tables & compiled MD documents
      - chroma_cache:/root/.cache/chroma    # Caches the local vector models permanently
```

* **`sqlite_data`:** Maps internal data directories outward to host allocations. Retains `agent_archive.db` and autogenerated markdown solutions.
* **`chroma_cache`:** Bridges the persistent directory for local embeddings. This completely bypasses the `79.3MB` model file download cycle (`all-MiniLM-L6-v2/onnx.tar.gz`) during consecutive execution intervals, reducing startup latencies to near zero.

### 💡 Podman Rootless Permission Note
Because Podman runs in user-space (rootless) by default, you may occasionally encounter permission blocks writing to mounted directories. If container errors throw write-access faults, apply sub-uid adjustments on the host machine:
```bash
podman unshare chown -R 1000:1000 ./db_data
```

## 🔍 Validation, Monitoring & Verification

Once setup signals absolute uptime, confirm component operational integrity via standard host inspection channels:

### 1. View Engine Allocation States
```bash
podman ps
```
*Ensure both `ai_scientist_agents` (Port `8500`) and `ai_scientist_agents_chromadb` (Port `8000`) present active execution health statuses.*

### 2. Tail Streamed Agent Diagnostics
Track agent analytical deliberations, search mutations, embedding additions, and DeepSeek validation thoughts directly via stdout streams:
```bash
podman logs -f ai_scientist_agents
```

### 3. Conduct Integration Flight Test
Issue a test payload from your terminal to verify end-to-end functionality:
```bash
curl -X POST http://localhost:8500/api/ask \
     -H "Content-Type: application/json" \
     -d '{"prompt": "Skriv en nodejs-funktion som skriver hello world i konsollen."}'
```
